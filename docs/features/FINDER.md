# Finder presentation and dmgbuild parity (D-FINDER-01 through D-FINDER-03)

Target is all applicable stable dmgbuild settings with explicit deferrals (see compatibility inventory). Reference S06 (stable settings and source). Preserve serialized semantics, not every historical quirk or Python execution environment. Current docs describe 2.0 settings; also retain legacy format/coverflow recognition. Native Finder behavior is separately tested for supported macOS builds. Never claim pixel-exact appearance from cross-platform simulation.

## Model and default behavior

`FolderPresentation` contains `window_position` (screen-coordinate semantics compatible with imported settings, y-axis conversion explicitly tested), `window_size` in points, `default_view`, window chrome flags, sidebar width, background variant, icon view, list view, and items. `finder` root table is the root layout; `[[finder.folders]]` extends it for a canonical existing folder with `path` and optional overrides. Folder settings do not independently control each item's displayed icon size: icon view size belongs to the folder; `volume_icon.images` and custom icons supply multiple resolutions. Positions are points not device pixels; treat top/left and center conversion explicitly. `icon-view`, `list-view`, `column-view`, `coverflow` recognized; gallery as dmgez extension only after evidence. Non-icon settings may not be respected on modern Finder; preserve values, label unsupported behavior. Default icon-view, 640x280 pt, position [100,100], no chrome, text 16 pt and icon 128 pt are proposed conventional defaults; grid spacing 80 (<100 warning in docs). Window positions may be adjusted by Finder on different displays. Keep `show_icon_preview` and `show_item_info` as separate properties. `include_icon_view_settings` and `include_list_view_settings` accept bool or `auto`, default auto; when forced false cannot remove required default view data without error. `arrange_by=none` default honors explicit positions; explicit positions with automatic arrangement warn they may be ignored. `grid_offset`, `grid_spacing`, `scroll_position`, `label_position=bottom|right`, `text_size`, `icon_size`, `positions` by destination name. Reject conflicting per-entry and per-folder positions. Validate actual folder-local entry names, not host basenames. Lint icon/label overlaps, clipping, invisible targets, image scale, sort overrides and nonnative coverflow. Do not silently reposition user entries in build; optional GUI alignment tools are explicit edits.

List view has `icon_size`, `text_size`, `scroll_position`, `sort_by`, `use_relative_dates`, `calculate_all_sizes`, `columns`, `column_widths`, `sort_directions`. Columns ordered and unique from name/date-modified/date-created/date-added/date-last-opened/size/kind/label/version/comments; widths and directions for all known columns, even hidden columns when serializing supported options. Validate positive finite widths and sort field; default name ascending. No arbitrary per-item sort order hidden in model. Preserve flags not recognized only in actual image inspection/rebuild with safe raw-record passthrough; report unknown record types. Do not copy `.DS_Store` implementation; `ds_parser` dependency must prove it can write required records/unknown preservation under tests. If necessary extend upstream or implement a narrow adapter rather than silently dropping fields.

## Generated files and identity ordering

Root `.DS_Store` and optional folder stores built directly. Typical layout uses Finder window properties (`bwsp`), icon view properties (`icvp`), list view (`lsvp`), view kind (`icvl`), item location (`Iloc`) and background references (evidence-qualified record codes). Treat names, FourCC, plist payloads, endian and numeric encodings as fixture-verified data; no copied implementation. Reserve generated `.background` (or explicit collision-free generated namespace), `.VolumeIcon.icns`, and metadata stores before catalog IDs allocated. Use final volume/file IDs, path and timestamps in `alias_record` for background, not temporary host disk IDs. HFS+ builder exposes a draft identity registry before final content lengths and allocation; see C3. Background may be plain color, file image, optional higher-res image or independently drawn built-in arrow/template. Store actual assets and references in image, mark generated hidden as needed. `image` or TIFF writer qualification required to combine Retina scale reps; prebuilt multi-res background supported without processing if compatible. Color parser accepts named CSS colors, hex, rgb/hsl/hwb/cmyk syntaxes supported by dmgbuild as qualified, range-check and convert deterministically. No asset is fetched from network implicitly. Background strings map to unambiguous tagged form; canonical TOML inline `background={kind="image",source="...",retina="..."}` or `kind="color",value=...` / `kind="template",name=...` / `kind="none"`. File and template paths validated relative to project. User-supplied artwork must be licensed. Do not bundle Apple artwork or font binaries.

`volume_icon.source` accepts existing ICNS without recompression if valid; `images` table of point sizes and scale reps creates ICNS with `icns` using supplied PNGs. Validate actual pixel dimensions: e.g. 16 points @2x needs 32x32, 512 @2x needs 1024x1024. 16/32/128/256/512 and their @2x representations are target set; unsupported sizes error. `badge` uses independent rendering assets with optional `image-processing` (do not ship proprietary generic Apple volume icon). Resize from one source optional; multiple pre-rendered reps can be used without broad processing. `.VolumeIcon.icns` plus correct root Finder volume custom-icon flag; do not apply file-icon flag to arbitrary signed app bundles. Per-file/folder custom icons need correct resource fork, Finder flags and special child conventions; preserve original signature or reject. Applications shortcut is a symlink `/Applications`, not an alias. On other hosts it is an explicit virtual action, never resolve `/Applications` as a host folder automatically.

## Tests and support

The Finder writer can encode a supplied file alias into the image-background record. The [wire tests](../../crates/presentation/dmgez-finder/tests/background_alias.rs) verify the alias payload with independent decoders, including volume and catalog IDs, timestamps, and path. Reserving and binding the background file during project builds and qualifying Finder's native alias resolution remain open.

Generate `dmgbuild` settings fixtures (synthetic inputs) for each inventory entry, compare decoded semantics not incidental B-tree bytes. For native macOS test attach and open actual image, verify background alias resolution, root custom volume icon, item positions, icon/list settings, hidden items and extensions, multi-res backgrounds, nested folder settings. Use separate visual tolerances for Finder font and geometry; stable synthetic icons for cross-platform screenshot tests. Never force unsupported views to icon-view without reporting. Compare read -> edit -> write retains unaffected raw records where explicitly supported; unknown alias/version refuse lossless rewrite when uncertain. `legacy` and `license` deferrals explicit in inventory; no arbitrary Python evaluation. `appdmg` JSON import in 0.3 is a safe translation of known fields only, unknown fields diagnostic. Python settings migration guide documents mappings, not unsafe execution.

The optional `import-appdmg` CLI validates translated version-one TOML before writing a new manifest. Asset paths are anchored lexically to the settings directory, and explicit symlink targets stay verbatim. The build still applies its normal source-identity and symlink rules. Unknown fields and unsupported options produce import errors. Image-based sizing and automatic Retina discovery are reported for explicit configuration. See the [appdmg specification](https://github.com/LinusU/node-appdmg#specification) and [CLI migration cases](../../apps/dmgez-cli/tests/import_appdmg_cli.rs) for the import profile and its `D-FINDER-03` checks.
