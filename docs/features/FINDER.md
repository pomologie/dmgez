# Finder presentation and dmgbuild parity (D-FINDER-01 through D-FINDER-03)

Target is all applicable stable dmgbuild settings with explicit deferrals (see compatibility inventory). Reference S06 (stable settings and source). Preserve serialized semantics, not every historical quirk or Python execution environment. Current docs describe 2.0 settings; also retain legacy format/coverflow recognition. Native Finder behavior is separately tested for supported macOS builds. Never claim pixel-exact appearance from cross-platform simulation.

## Model and default behavior

`FolderPresentation` contains `window_position` (screen-coordinate semantics compatible with imported settings, y-axis conversion explicitly tested), `window_size` in points, `default_view`, window chrome flags, sidebar width, background variant, icon view, list view, and items. `finder` root table is the root layout; `[[finder.folders]]` extends it for a canonical existing folder with `path` and optional overrides. Folder settings do not independently control each item's displayed icon size: icon view size belongs to the folder; `volume_icon.images` and custom icons supply multiple resolutions. Positions are points not device pixels; treat top/left and center conversion explicitly. `icon-view`, `list-view`, `column-view`, `coverflow` recognized; gallery as dmgez extension only after evidence. Non-icon settings may not be respected on modern Finder; preserve values, label unsupported behavior. Default icon-view, 640x280 pt, position [100,100], no chrome, text 16 pt and icon 128 pt are proposed conventional defaults; grid spacing 80 (<100 warning in docs). Window positions may be adjusted by Finder on different displays. Keep `show_icon_preview` and `show_item_info` as separate properties. `include_icon_view_settings` and `include_list_view_settings` accept bool or `auto`, default auto; when forced false cannot remove required default view data without error. `arrange_by=none` default honors explicit positions; explicit positions with automatic arrangement warn they may be ignored. `grid_offset`, `grid_spacing`, `scroll_position`, `label_position=bottom|right`, `text_size`, `icon_size`, `positions` by destination name. Reject conflicting per-entry and per-folder positions. Validate actual folder-local entry names, not host basenames. Lint icon/label overlaps, clipping, invisible targets, image scale, sort overrides and nonnative coverflow. Do not silently reposition user entries in build; optional GUI alignment tools are explicit edits.

List view has `icon_size`, `text_size`, `scroll_position`, `sort_by`, `use_relative_dates`, `calculate_all_sizes`, `columns`, `column_widths`, `sort_directions`. Columns ordered and unique from name/date-modified/date-created/date-added/date-last-opened/size/kind/label/version/comments; widths and directions for all known columns, even hidden columns when serializing supported options. Validate positive finite widths and sort field; default name ascending. No arbitrary per-item sort order hidden in model. Preserve flags not recognized only in actual image inspection/rebuild with safe raw-record passthrough; report unknown record types. Do not copy `.DS_Store` implementation; `ds_parser` dependency must prove it can write required records/unknown preservation under tests. If necessary extend upstream or implement a narrow adapter rather than silently dropping fields.

## Generated files and identity ordering

Root `.DS_Store` and optional folder stores built directly. Typical layout uses Finder window properties (`bwsp`), icon view properties (`icvp`), list view (`lsvp`), view kind (`icvl`), item location (`Iloc`) and background references (evidence-qualified record codes). Treat names, FourCC, plist payloads, endian and numeric encodings as fixture-verified data; no copied implementation. Reserve generated `.background` (or explicit collision-free generated namespace), `.VolumeIcon.icns`, and metadata stores before catalog IDs allocated. Use final volume/file IDs, path and timestamps in `alias_record` for background, not temporary host disk IDs. HFS+ builder exposes a draft identity registry before final content lengths and allocation; see C3. Background may be plain color, file image, optional higher-res image or independently drawn built-in arrow/template. Store actual assets and references in image, mark generated hidden as needed. `image` or TIFF writer qualification required to combine Retina scale reps; prebuilt multi-res background supported without processing if compatible. Color parser accepts named CSS colors, hex, rgb/hsl/hwb/cmyk syntaxes supported by dmgbuild as qualified, range-check and convert deterministically. No asset is fetched from network implicitly. Background strings map to unambiguous tagged form; canonical TOML inline `background={kind="image",source="...",retina="..."}` or `kind="color",value=...` / `kind="template",name=...` / `kind="none"`. File and template paths validated relative to project. User-supplied artwork must be licensed. Do not bundle Apple artwork or font binaries.

`volume_icon.source` accepts existing ICNS without recompression if valid; `images` table of point sizes and scale reps creates ICNS with `icns` using supplied PNGs. Validate actual pixel dimensions: e.g. 16 points @2x needs 32x32, 512 @2x needs 1024x1024. 16/32/128/256/512 and their @2x representations are target set; unsupported sizes error. `badge` uses independent rendering assets with optional `image-processing` (do not ship proprietary generic Apple volume icon). Resize from one source optional; multiple pre-rendered reps can be used without broad processing. `.VolumeIcon.icns` plus correct root Finder volume custom-icon flag; do not apply file-icon flag to arbitrary signed app bundles. Per-file/folder custom icons need correct resource fork, Finder flags and special child conventions; preserve original signature or reject. Applications shortcut is a symlink `/Applications`, not an alias. On other hosts it is an explicit virtual action, never resolve `/Applications` as a host folder automatically.

## Tests and support

The bounded store reader decodes list view from both the keyed `lsvp` and ordered `lsvC` binary plist records. It preserves each record independently because Finder can store different columns in each. Keyed columns follow their stored indices, and ordered columns follow the stored array. Reports include column identifiers, widths, visibility and direction, together with the admitted list settings and the names of unreported settings. The reader bounds nesting and shared-reference expansion before decoding. [Finder-written Sonoma fixture and reader tests](../../crates/presentation/dmgez-finder/tests/list_view.rs)

Root and nested Finder layouts accept `default_view = "column-view"`. The generated `.DS_Store` selects column view with the `icvl/type/clmv` record. A nested folder inherits the selected view and can override it. Icon positions remain available when switching views, and explicit `include_icon_view_settings` and `include_list_view_settings` still control their secondary settings.

The D-FINDER-02 compatibility check verified and mounted an HFS+ image read-only on macOS 14.7.2. The independent `ds_store` reader matched the selected view, nested override, icon position, and secondary records. Actual Finder window selection remains unverified because macOS denied this runner's Apple Event request. The desktop preview still requires icon view. [Mounted column view check](../../tests/compatibility/project-build/check_finder_column.py) [dmgbuild column view mapping](https://github.com/dmgbuild/dmgbuild/blob/v2.0.0/src/dmgbuild/core.py#L450-L464)

HFS+ project builds support static PNG backgrounds, paired Retina PNGs, and a prebuilt two-representation TIFF in the root and configured folders. The builder captures and revalidates every input file, reserves a hidden `/.background` directory and its files, and reuses the same asset for inherited settings. A local folder may select another source or pair or override the inherited background with a solid color. After the HFS+ draft assigns catalog IDs, the builder writes the aliases from the stored Unicode volume label, creation timestamps, and file and parent IDs. Each alias contains the standard `/Volumes/<volume name>` mount hint.

```toml
[finder]
background = { kind = "image", source = "artwork/Background.png", retina = "artwork/Background@2x.png" }
```

The high-resolution PNG must be exactly twice the base width and height. The builder writes the base followed by the Retina representation at 72 and 144 dpi, which gives both the same size in points. The generated classic TIFF uses uncompressed strips, preserves supported PNG samples and transparency, and carries compatible embedded ICC profiles. PNG animation, orientation metadata, HDR, and standalone gamma or chromaticity outside the supported color profile are rejected during planning. These restrictions apply to conversion. A source-only PNG is validated and stored byte for byte. [Apple high-resolution image guidance](https://developer.apple.com/library/archive/documentation/GraphicsAnimation/Conceptual/HighResolutionOSX/Optimizing/Optimizing.html)

For a prebuilt TIFF, set `source` and omit `retina`. The builder identifies the TIFF by its header, validates two top-left, strip-based 1× and 2× representations with equal sizes in points, and stores the original bytes. The supported prebuilt pixel layouts are unsigned 8- or 16-bit grayscale and RGB, with optional alpha. The TIFF may use uncompressed, LZW, Deflate, or PackBits strips. Encoded source size, dimensions, decoder memory, and retained asset bytes are bounded by build limits.

Set `background = { kind = "template", name = "builtin-arrow" }` to generate an original centered blue arrow on a neutral 640 × 280 point canvas. The generated TIFF holds 640 × 280 and 1280 × 560 pixel representations at 72 and 144 dpi. Root and inherited folder layouts reuse one hidden asset. Local layouts can select a different background. The template reserves the same namespace and binds the same catalog identities as a file-backed background. [dmgbuild's built-in background setting](https://dmgbuild.readthedocs.io/en/stable/settings/#background)

On macOS 14.7.2 (23H311), arm64, Apple verified and checked a generated image with the built-in template and a badged icon. Core Foundation resolved both inherited aliases to the same mounted TIFF and matched its catalog IDs. AppKit reported a 640 × 280 point image at both scales, and ImageIO verified the canvas and arrow pixels in each TIFF page. [Combined native check](../../tests/compatibility/project-build/check_finder_artwork.py)

The native background check passed on macOS 14.7.2 (23H311), arm64, for two static PNG builds, a paired Retina build, and a prebuilt TIFF from Apple's `tiffutil`. Apple verified and checked all four images before mounting them read-only. Core Foundation resolved the aliases to the expected files and the mounted file and parent IDs matched the records. ImageIO matched both Retina representations to the source pixels, and AppKit selected the corresponding representations at 1× and 2×. The Python oracle also checked nested image and color overrides. Visual verification in a Finder window remains open. [Native check](../../tests/compatibility/project-build/check_finder_background.py) [Wire tests](../../tests/compatibility/project-build/tests/smoke/retina_background_oracle.py)

Solid backgrounds use `background = { kind = "color", value = "goldenrod" }`. Opaque CSS keywords, three- and six-digit RGB hex, and comma-separated `rgb`, `hsl`, `hwb`, `cmyk`, `gray`, and `grey` are supported. Channels use fractions from 0 to 1 or percentages from 0 to 100%. Hue defaults to degrees and also accepts `deg`, `rad`, `grad`, and `gon`. Invalid channels and alpha forms fail preflight. The desktop preview uses the same parser. The composed test compares decoded Finder RGB values to dmgbuild 2.0.0 for the overlapping forms and checks the documented integer, default-degree, and percentage forms. [dmgbuild settings](https://dmgbuild.readthedocs.io/en/stable/settings/) [Color compatibility tests](../../tests/compatibility/project-build/tests/smoke/color_background.rs)

With `volume-icon` enabled, use `[volume_icon.images]` to build an ICNS from an explicit nonempty set of PNG representations. Each key selects a logical size and scale. The builder verifies the corresponding physical pixel dimensions, captures every input as a regular local file, and revalidates it before publication. An existing `volume_icon.source` ICNS remains byte-preserving. [Volume icon profile](../reference/VOLUME_ICON.md)

The optional `badge-icons` feature enables `volume_icon.badge`. dmgez fits the badge over an original drive glyph and renders all ten ICNS slots, preserving the selected source's aspect ratio and transparency. This uses the same catalog flag, source identity checks, and publication rules as other volume icons. [Volume icon profile](../reference/VOLUME_ICON.md)

With `volume-icon` enabled, an individual `[[contents]]` entry can set `custom_icon = "artwork/Document.icns"`. The ICNS must meet the prebuilt icon profile. A regular file receives the `icns` resource and Finder custom-icon flag while retaining its data fork. A directory receives the flag and one invisible `Icon\r` child with an empty data fork. Directory icons require the HFS+ Unicode catalog profile because that child name ends with a carriage return. The resource fork stores the original ICNS unchanged. [Apple Finder information format](https://developer.apple.com/library/archive/technotes/tn/tn1150.html#FinderInfo)

The builder refuses symlink targets, preserved shared inodes, an existing file resource fork, and a conflicting folder child. It also refuses icons on items inside application bundles, bundles with recognized signature markers, signed Mach-O executables, and files with native code-signing attributes. A renamed application or framework remains protected when its signature marker identifies it. The source artwork is identity-checked before publication. [Apple code-signing metadata restrictions](https://developer.apple.com/library/archive/qa/qa1940/_index.html)

The native check covers the per-item icon portion of D-FINDER-03-T01. On macOS 14.7.2 (23H311), arm64, `hdiutil` verified and mounted the HFS+ image read-only. AppKit matched both mounted icons to the source ICNS at 16, 32, and 128 pixels. The check also compared the Finder flags, both complete resource forks, and the original file data. [Native item icon check](../../tests/compatibility/project-build/check_finder_item_icons.py)

Apple's `codesign --verify --strict` verified ad-hoc signed applications, a renamed framework, a standalone Mach-O executable, and a shell script. dmgez refused the icon requests and preserved the existing output. The fixtures passed strict verification again afterward. This covers the signed-target refusal portion of D-FINDER-03-T01. [Native signing check](../../tests/compatibility/project-build/check_signed_item_icon.py)

Generate `dmgbuild` settings fixtures (synthetic inputs) for each inventory entry, compare decoded semantics not incidental B-tree bytes. For native macOS test attach and open actual image, verify background alias resolution, root custom volume icon, item positions, icon/list settings, hidden items and extensions, multi-res backgrounds, nested folder settings. Use separate visual tolerances for Finder font and geometry; stable synthetic icons for cross-platform screenshot tests. Never force unsupported views to icon-view without reporting. Compare read -> edit -> write retains unaffected raw records where explicitly supported; unknown alias/version refuse lossless rewrite when uncertain. `legacy` and `license` deferrals explicit in inventory; no arbitrary Python evaluation. `appdmg` JSON import in 0.3 is a safe translation of known fields only, unknown fields diagnostic. Python settings migration guide documents mappings, not unsafe execution.

The optional `import-appdmg` CLI validates translated version-one TOML before writing a new manifest. Asset paths are anchored lexically to the settings directory, and explicit symlink targets stay verbatim. The build still applies its normal source-identity and symlink rules. Unknown fields and unsupported options produce import errors. Image-based sizing and automatic Retina discovery are reported for explicit configuration. See the [appdmg specification](https://github.com/LinusU/node-appdmg#specification) and [CLI migration cases](../../apps/dmgez-cli/tests/import_appdmg_cli.rs) for the import profile and its `D-FINDER-03` checks.
