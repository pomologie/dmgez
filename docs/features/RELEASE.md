# Signing, notarization, release validation and lint (D-REL-01 through D-REL-04)

The default CLI includes a pinned `apple-codesign` backend for offline ad hoc DMG signing on macOS, Linux, and Windows. `auto` selects that backend for ad hoc DMG signing. The optional native macOS backend performs Developer ID signing, notarization, stapling, and platform assessment. A release fixes its selection before signing. Signing keys and Apple service credentials are supplied through authorized providers and stay out of `dmg.toml`. [Upstream signer source](https://github.com/indygreg/apple-platform-rs/tree/apple-codesign%2F0.29.0/apple-codesign)

## Pipeline

1. Plan inputs, validate credentials/capabilities without exposing secrets. Stage source apps if sign requested; default `[signing].apps="verify"` checks existing signatures and does not re-sign. `preserve` packages without claiming validity; `sign` explicit and stage only. Inspect nested Mach-O, frameworks, plugins, helpers, dylibs, bundles; per-path signing policy/entitlements, sign inside-out; no blind `codesign --deep` for signing. Preserve symlinks and resources. Validate Developer ID Application identity, secure timestamps, hardened runtime for eligible executables, and entitlement policy; signing alone does not satisfy Apple requirements.
2. Build unsigned DMG from staged/preserved app, verify structure and requested manifest. Signing DMG afterward may alter trailer and signature regions; use correct qualified backend, not homegrown cryptographic signing. Capture unsigned digest for reproducibility; signed digest distinct. Never modify signed bundle just to change icons. Edits to signed images invalidate signature/ticket unless verified otherwise; report and require re-signing, never retain stale trust badge.
3. Submit signed artifact to Apple notarization service using chosen backend. Requires network, eligible account and credentials, exact submitted artifact digest. Persist a private nonsecret submission record with submission ID, digest, backend, timestamp/status; resume polls by ID, never blindly resubmit ambiguous upload. `--wait` or explicit status subcommand; no background service needed. Bounded backoff/retry and cancellation; pending/accepted/rejected/unknown distinct. Save redacted diagnostics/notary log. Cancellation of local polling does not cancel Apple's remote process; communicate this. Apple acceptance not equivalent to running correctly.
4. Staple accepted ticket to exact staged artifact; validate ticket via supported backend, native `stapler validate` where available. Reopen final image and verify structural integrity and unchanged disk semantics. On native macOS test trusted signed app, actual mount/copy, signature validity and current Gatekeeper assessment appropriate to OS version (qualify `spctl`/`syspolicy_check` etc. by target). Rust signature inspection/cryptographic checks are not native policy evaluation. A ticket's presence is not proof of acceptance or validity. No network by default outside explicit release actions.
5. Produce `ReleaseReport`: per-stage required/optional/skipped, passed/failed/pending/unavailable, backend/version, artifact digest, cert fingerprint/nonsecret selector, notary ID/status, structural and native policy checks. `require_notarization` and `require_native_assessment` must fail release if required evidence unavailable, not mark skipped success. Stage commit only after all required gates pass. User may retain failed artifact/log explicitly outside final release path; do not publish invalid output.

### Portable signing profile

Ordinary macOS, Linux, and Windows CLI builds include offline DMG signing. Build with `--no-default-features` to omit the default backend. Signing runs through an explicit release or sign command. D-REL-01-T04 covers backend selection and ordinary builds on each host.

```toml
identifier = "com.example.installer"
```

```sh

```

The 0.29 DMG writer places the signature immediately after the XML plist and uses a 32-bit CodeDirectory length. The UDIF signing guard checks that the plist ends at the original trailer, all declared body ranges stay inside the signed body, and the body length fits that field. ## Semantic diff and lint policies

Diff supports `contents` (BLAKE3 + optional exact stream compare), metadata, links, resource forks/xattrs, Finder semantic settings, filesystem allocation/raw records, UDIF physical maps/codec/byte differences, signature metadata; physical and logical differences separate. Compare normalized paths with each filesystem's rules; case/normalization ambiguities diagnostic. Compare volume IDs/profile explicitly. No implicit timestamp suppression; optional policy ignores listed fields and reports exclusions. Detect unchanged/added/removed/changed/renamed candidate (rename inference clearly labeled). Budgeted traversal, hash cache scoped to immutable identity, parallel only as allowed. Return machine diff including unknown/not compared. CI exit 0 equal under policy, 1 differences, 2 error/unsupported. Lint profiles `installer`, `macos-release`, `layout`, `strict-metadata` use typed rule IDs severity and evidence, suppressions explicit with reason. Rules: missing expected Applications link, incorrect target, overlapping icons/labels, background missing, size/scale mismatch, unsafe path, duplicate canonical names, suspicious external symlink (normal Applications link allowed), unexpected visible private assets, missing executable mode/Info.plist executable, missing signature/hardened runtime/ticket where requested. Lint never auto-fixes signed content; suggested changes separate. Release checks run native tools only when explicitly requested.

### Compare filesystem contents

For a CLI composed with `diff` and the selected reader, `diff LEFT RIGHT --mode semantic --filesystem hfsplus|apfs` compares two opened volume trees. Each side can select a raw image, partition slot, and, for APFS, a volume UUID or object ID and exact retained XID. Diagnosed APFS checkpoint recovery requires an explicit retained XID on the affected side. Reports identify both selected disk windows and include HFS+ or HFSX signatures or APFS volume and checkpoint identities. The outcome describes the tree comparison policy.

The baseline policy matches exact stored Unicode spellings and reports paths as arrays of components. It compares object kind, POSIX mode and ownership, visible hard-link groups and counts, symlink targets, and regular-file data and resource forks. Forks compare by exact bytes and available stream presence. HFS+ exposes an empty stored resource descriptor as a zero-length stream. APFS reports absence when the resource attribute is missing. The report lists its policy, limits, and exclusions, including timestamps, Finder settings, allocation records, and signatures.

Use `--paths native` when both volumes expose the same qualified name profile. HFS+ and case-folded HFSX use the historical comparator on stored decomposed UTF-16. Binary HFSX uses exact stored UTF-16 units. APFS with both name-insensitivity flags clear uses exact stored UTF-8. Normalization-insensitive APFS uses canonical decomposition, with full case folding for a case-insensitive volume. These two APFS profiles admit scalars assigned through Unicode 9. Names outside that repertoire stop native comparison with a typed diagnostic, and `--paths exact` retains access to their stored spellings. Differing profiles and ambiguous paths fail with diagnostics. The library's `Limits::max_path_bytes` also bounds native key bytes independently on each side. [HFS+ catalog name comparison](https://developer.apple.com/library/archive/technotes/tn/tn1150.html#UnicodeSubtleties) [APFS name semantics](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html)

The native report includes the selected profile. A changed pair uses the stored left path and includes `right_path` when the spelling differs. `equivalent_path_spellings` records spelling differences for pairs whose compared fields agree. Path spelling differences under the native policy do not change the outcome on their own. Hard-link groups and rename inference use the paired namespace. The default `--paths exact` keeps stored spellings significant.

With `diff-hash` compiled, use `--contents blake3` to hash equal-length data and resource forks on matched regular files. `--contents blake3-exact` also confirms matching digests with an exact stream comparison. Each pass consumes the shared byte budget. The hash pass reuses digests of validated hard-link storage within the same opened view and fork. Exact confirmation reads both forks for each matching path. Length and presence remain part of fork equality. Symlink targets, Finder settings, and optional extended attributes use their own comparison policies. The default is `--contents exact`.

Use `--infer-renames` to list candidate pairs among unmatched regular-file paths without shared hard-link storage. Each pair needs a unique data and resource fork fingerprint on each side, including fork presence and lengths, and at least one nonempty fork. The hash index lives for a single comparison. Candidates appear separately from the added and removed changes. Same-content deletion and copying can produce the same evidence as moving a file. The larger of the total fingerprint bytes read on either side charges the shared budget. Candidate fingerprints use BLAKE3 independently of the selected policy for matched files.

Add `--xattrs` to compare stored attribute names and exact values on common paths. Complete listings establish whether a name was added or removed, including a present empty value. Values for matching names share the fork payload budget. Reports contain names and change kinds. An uncheckable listing, invalid name, unreadable matching value, or exhausted budget stops the comparison. The policy identifies its name limits and excluded records for resource forks, Finder info, compression, symbolic links, and access-control lists. Quarantine records compare as stored bytes. Trust assessment remains separate.

Add `--finder-info` to compare the effective 32-byte FinderInfo and its presence on common paths of the same supported kind. HFS+ and HFSX read the catalog metadata behind each regular-file hard link, mask the kernel's private fields, and treat an empty projected value as absent. APFS reads one admitted FinderInfo representation from the owning inode or its inline attribute. Symbolic links are inspected in place. Reports identify changed paths with `finder_info` and omit the bytes. The comparison charges 32 bytes for a pair with a value on either side and stops if the selected reader cannot establish an object's FinderInfo. `--finder-info` uses the same composed reader as the baseline comparison and can be combined with either additional metadata policy. [HFS+ FinderInfo projection](https://github.com/apple-oss-distributions/hfs/blob/main/core/hfs_xattr.c#L288-L367) [Apple File System Reference](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf#page=111)

Matching files still receive the other enabled comparisons, including resource forks, `--xattrs`, and `--finder-info`.

The Finder profile admits single-leaf stores within the reader's byte, record, name, and plist limits. The larger of the two complete store lengths is charged to the shared logical byte budget. Exit 0 means there are no unsuppressed warnings, exit 1 means warnings remain, and exit 2 means the inspection could not finish. ### Test a finished installer

On macOS or Linux, compose the CLI with `installer-test` and a local HFS+ or APFS reader. Run `dmgez test installer.dmg --profile installer --json`. Use `--filesystem apfs` and the usual `--volume` and `--xid` selectors to choose an APFS volume or checkpoint. `--partition` selects a data partition. The check holds the image open and revalidates its file identity. It verifies UDIF payload and all required CRC domains, then checks top-level application layouts, the exact `/Applications` shortcut, and the stored targets of symbolic links. It reads bundle declarations and executable metadata directly from the volume. No app is launched or image mounted. [Shared installer test workflow](../../crates/runtime/dmgez-runtime/src/installer_test.rs) [Installer image rules](../../crates/runtime/dmgez-operations/src/install/check.rs)

Request `--require-signature`, `--require-ticket`, or `--require-native-assessment` independently. Static DMG signature verification accepts a valid ad hoc signature and gives no Developer ID or Gatekeeper verdict. Native ticket validation checks an existing stapled ticket and may consult Apple’s ticket service. Native assessment uses the current macOS policy. The native checks require their corresponding signing or notarization feature and report unavailable when the host or tool cannot provide evidence. The report keeps those checks separate from each other and from filesystem layout. A malformed container blocks further checks.

Exit 0 means all selected checks passed. Exit 1 reports failed checks such as a checksum mismatch, invalid app layout, unsigned DMG, or missing ticket. Exit 2 reports an unavailable required check or an operational error. The image tests cover read-only verification of a synthetic HFS+ installer and native ad hoc signing, rejection of a corrupt container, and a native APFS checkpoint without an application. Live accepted ticket validation and native policy acceptance require separate qualification.
