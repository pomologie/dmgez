# Signing, notarization, release validation and lint (D-REL-01 through D-REL-04)

Use shared release stages over existing DMG and application artifacts. Optional `apple-codesign` Rust backend, native macOS backend orchestrating codesign, notarytool, stapler, and native assessment tools. Only sign with user-authorized Developer ID identities and Apple service credentials; no private key embedded in source/config, no Gatekeeper bypass. Apple guidance S09-S10. Distinguish `native` on macOS, `rust` cross-platform, `auto` explicit capability resolution per operation (prefer usable native on macOS; otherwise Rust if compatible). Select backend during plan; log chosen backend and reasons, do not silently change after side effects or failed authorization. Backend-specific support for DMG signing/stapling and bundle signing must be verified against actual pinned library API; do not promise native parity. `apple-codesign` may depend transitively on `apple-dmg`, allowed for signing only. DMG builder itself remains independent. Native tools use trusted paths and argument arrays, fixed environment/timeout; never shell interpolation.

## Pipeline

1. Plan inputs, validate credentials/capabilities without exposing secrets. Stage source apps if sign requested; default `[signing].apps="verify"` checks existing signatures and does not re-sign. `preserve` packages without claiming validity; `sign` explicit and stage only. Inspect nested Mach-O, frameworks, plugins, helpers, dylibs, bundles; per-path signing policy/entitlements, sign inside-out; no blind `codesign --deep` for signing. Preserve symlinks and resources. Validate Developer ID Application identity, secure timestamps, hardened runtime for eligible executables, and entitlement policy; signing alone does not satisfy Apple requirements.
2. Build unsigned DMG from staged/preserved app, verify structure and requested manifest. Signing DMG afterward may alter trailer and signature regions; use correct qualified backend, not homegrown cryptographic signing. Capture unsigned digest for reproducibility; signed digest distinct. Never modify signed bundle just to change icons. Edits to signed images invalidate signature/ticket unless verified otherwise; report and require re-signing, never retain stale trust badge.
3. Submit signed artifact to Apple notarization service using chosen backend. Requires network, eligible account and credentials, exact submitted artifact digest. Persist a private nonsecret submission record with submission ID, digest, backend, timestamp/status; resume polls by ID, never blindly resubmit ambiguous upload. `--wait` or explicit status subcommand; no background service needed. Bounded backoff/retry and cancellation; pending/accepted/rejected/unknown distinct. Save redacted diagnostics/notary log. Cancellation of local polling does not cancel Apple's remote process; communicate this. Apple acceptance not equivalent to running correctly.
4. Staple accepted ticket to exact staged artifact; validate ticket via supported backend, native `stapler validate` where available. Reopen final image and verify structural integrity and unchanged disk semantics. On native macOS test trusted signed app, actual mount/copy, signature validity and current Gatekeeper assessment appropriate to OS version (qualify `spctl`/`syspolicy_check` etc. by target). Rust signature inspection/cryptographic checks are not native policy evaluation. A ticket's presence is not proof of acceptance or validity. No network by default outside explicit release actions.
5. Produce `ReleaseReport`: per-stage required/optional/skipped, passed/failed/pending/unavailable, backend/version, artifact digest, cert fingerprint/nonsecret selector, notary ID/status, structural and native policy checks. `require_notarization` and `require_native_assessment` must fail release if required evidence unavailable, not mark skipped success. Stage commit only after all required gates pass. User may retain failed artifact/log explicitly outside final release path; do not publish invalid output.

## CLI/config

`sign inspect`, `sign app`, `sign dmg`, `sign verify`, `notarize [--wait]`, `notarize status ID`, `staple`, `lint --profile macos-release`, `test --profile installer`, `build --release`. All explicit signing/notary actions behind appropriate features; default `build` ignores no requested behavior: if config sets enabled but command lacks `--release`, report that configured stages were not executed; do not claim release-ready. `[signing] enabled, backend, apps, dmg, identity, credential_ref` and optional `[[signing.rules]]` match path and entitlements file; `[notarization] enabled, backend, wait, staple, credential_ref`; `[release] verify, require_notarization, require_native_assessment`. Secret references are opaque names resolved from Keychain, restricted environment or secure provider; no raw p12 content/password/private key allowed in TOML or CLI history. Use protected local file mode or stdin/secret provider where possible; avoid argv secrets and redact errors. Do not expose secrets to MCP, GUI logs, crash reports or test fixtures. Zeroize where possible. CI credentialed tests restricted to trusted branch and manually approved runner.

### Inspect and verify existing signatures

Build with `signing-native` and run `dmgez sign inspect ARTIFACT` or `dmgez sign verify ARTIFACT` on macOS. `--backend auto` selects the native backend on macOS. `--backend native` requires that backend explicitly. `--backend rust` currently reports unavailable. The native backend runs the fixed system `/usr/bin/codesign` with bounded output and a deadline. It accepts an app bundle directory or a UDIF v4 image. DMG admission checks the trailer header and requires unambiguous disk image identification in the native display output for a signed image. An ambiguous format record returns an operational error. Container integrity remains a separate check.

Inspect reports a readable signature as `present`. For Mach-O inspection, the native tool displays one architecture by default. Verify checks all architectures and nested code in app bundles. It reports the static signature result as `verified` or `failed`. Both commands can report an `unsigned` artifact. `--json` includes the selected backend, outcome, and bounded tool diagnostics. Exit 0 means the requested check succeeded, exit 1 means unsigned or failed, and exit 2 means unavailable or an operational error. The policy assessment field is `not_performed`. [Apple code signing guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html)

Before and after each tool call, dmgez compares the top-level path's identity and metadata. The signature result describes the artifact seen by the path-based native tool. For a stable release record, the release pipeline needs control of the staged artifact and its digest.

The read-only portion of D-REL-01-T01 was exercised on arm64 macOS 14.7.2 using a synthetic nested app and a UDZO image. The fixtures cover unsigned and ad hoc signed artifacts, tampering with a sealed nested resource and a signed image byte, and source bytes, modes, and xattrs before and after inspection. [Native signature fixtures](../../apps/dmgez-cli/tests/sign_cli.rs)

### Stage and sign a disk image

On macOS with `signing-native`, use the public SHA-1 fingerprint of an available Developer ID Application signing identity in Keychain. The identity's private key stays in Keychain. The signing operation contacts Apple's timestamp service. [Finding the signing identity and signing a disk image](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)

```sh
dmgez sign dmg installer.dmg --output installer-signed.dmg \
  --identity "$DEVELOPER_ID_FINGERPRINT" --identifier com.example.installer --json
```

The output parent must be a stable, trusted local directory. dmgez copies the unsigned UDIF bytes and any quarantine attribute into a private stage beside the output. It verifies the image CRC with `hdiutil` before signing and again afterward. The signed copy must keep the entire original body and every trailer field except the signature offset and length, satisfy a native requirement for the selected certificate and identifier, and carry a secure timestamp. Publication uses a no-clobber rename after those checks. The report includes the unsigned and signed SHA-256 digests. Filesystem consistency, notarization, and Gatekeeper remain separate checks. [Developer ID certificate requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)

The signing transaction was exercised on disposable UDRO and UDZO fixtures on arm64 macOS 14.7.2 with an ad hoc signer confined to the tests. The fixtures verify source and quarantine preservation, native CRC and signature checks, no new output after tampering or signature policy rejection, and preservation of an existing destination. A protected Developer ID run with Apple's timestamp service remains open for D-REL-01-T01. [Native staging fixtures](../../crates/security/dmgez-signing/src/native/disk/tests.rs)

### Stage and sign an application

On macOS with `signing-native`, use `sign app` with the public SHA-1 fingerprint of a Developer ID Application identity in Keychain. Supply distribution entitlements by exact bundle-relative signing target. Use `.` for the root bundle. Each declared target must be present in the plan. [Apple distribution signing workflow](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)

```sh
dmgez sign app Product.app --output Signed.app \
  --identity "$DEVELOPER_ID_FINGERPRINT" \
  --entitlements 'Contents/Helpers/Helper.app=helper.entitlements' --json
```

Keep the source bundle stable and use a trusted local output directory outside the source. dmgez copies through native `ditto` and checks resource bytes, modes, extended attributes, contained symlinks, and internal hard links before signing. macOS can update quarantine records during the copy. It signs each supported code item in the private copy before its enclosing bundle, including versions of versioned frameworks. Native verification checks the selected Developer ID certificate, secure timestamp, hardened runtime for eligible Mach-O executables, and the configured entitlements on each admitted architecture. An item with no rule has an empty entitlement policy. A final deep verification covers the app's nested signatures. The source is revalidated and the verified copy is published to a new path without clobbering an existing destination.

The CLI reports the signing order and the runtime and entitlement policy for each item. This operation replaces signatures in the staged copy. Policy assessment is reported as `not_performed`.

The private app transaction was exercised on arm64 macOS 14.7.2 with a previously signed synthetic app and nested helper. The fixtures verified inside-out re-signing, unchanged source files, hardened runtime, exact nested entitlements, and refusal to publish a failed verification. A protected Developer ID run remains open for D-REL-01-T01 and D-REL-01-T02. [Native app staging fixtures](../../crates/security/dmgez-signing/src/native/app/tests.rs)

### Submit and resume notarization

On macOS with `notarization-native`, `notarize` submits a signed UDIF image through Xcode's native `notarytool`. Use an existing Keychain profile. dmgez passes the profile name and stores neither it nor the underlying credentials in the submission record. [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)

```sh
dmgez notarize Signed.dmg --record Submission.json --keychain-profile "$NOTARY_PROFILE" --wait --json
dmgez notarize status "$SUBMISSION_ID" --record Submission.json --keychain-profile "$NOTARY_PROFILE" --json
```

Use a trusted local directory for the record. dmgez requires the record directory and the record itself to have no access control list, and it keeps the file at mode `0600`. It verifies the Developer ID signature and secure timestamp on a private copy of the exact image bytes. Before submitting, it reserves and syncs the record with the SHA-256, byte count, and local timestamps. When Apple returns the submission ID, dmgez saves it before polling. Another submit using that record path is refused. `--wait` polls with bounded backoff while the service reports pending. Ending a local wait leaves Apple processing the submission.

A timeout or malformed upload result leaves the record in an unknown state. Recover the candidate ID from the team's notary history and query it with the same record. With a reservation that has no saved ID, only a terminal Apple log with the matching ID and SHA-256 can bind the submission to the record. The same digest check gates terminal updates for records that already have an ID. Reports keep redacted issue counts and omit the raw log. `notarize status` also supports a remote-only query without `--record`; `digest_verified` then remains false because no local artifact digest was compared. [Apple submission status, history and logs](https://developer.apple.com/documentation/technotes/tn3147-migrating-to-the-latest-notarization-tool)

Exit 0 means pending or accepted, exit 1 means rejected, and exit 2 means unknown or an operational error. Local mock tests cover interrupted upload, repeated submission refusal, expired waits, rejection, and attempts to recover with a different digest. A protected Apple submission and stapling remain open for D-REL-02. [Notarization recovery fixtures](../../crates/security/dmgez-signing/src/notarization/flow/tests.rs)

## Semantic diff and lint policies

Diff supports `contents` (BLAKE3 + optional exact stream compare), metadata, links, resource forks/xattrs, Finder semantic settings, filesystem allocation/raw records, UDIF physical maps/codec/byte differences, signature metadata; physical and logical differences separate. Compare normalized paths with each filesystem's rules; case/normalization ambiguities diagnostic. Compare volume IDs/profile explicitly. No implicit timestamp suppression; optional policy ignores listed fields and reports exclusions. Detect unchanged/added/removed/changed/renamed candidate (rename inference clearly labeled). Budgeted traversal, hash cache scoped to immutable identity, parallel only as allowed. Return machine diff including unknown/not compared. CI exit 0 equal under policy, 1 differences, 2 error/unsupported. Lint profiles `installer`, `macos-release`, `layout`, `strict-metadata` use typed rule IDs severity and evidence, suppressions explicit with reason. Rules: missing expected Applications link, incorrect target, overlapping icons/labels, background missing, size/scale mismatch, unsafe path, duplicate canonical names, suspicious external symlink (normal Applications link allowed), unexpected visible private assets, missing executable mode/Info.plist executable, missing signature/hardened runtime/ticket where requested. Lint never auto-fixes signed content; suggested changes separate. Release checks run native tools only when explicitly requested.

### Compare filesystem contents

For a CLI composed with `diff` and the selected reader, `diff LEFT RIGHT --mode semantic --filesystem hfsplus|apfs` compares two opened volume trees. Each side can select a raw image, partition slot, and, for APFS, a volume UUID or object ID and exact retained XID. Diagnosed APFS checkpoint recovery requires an explicit retained XID on the affected side. Reports identify both selected disk windows and include HFS+ or HFSX signatures or APFS volume and checkpoint identities. The outcome describes the tree comparison policy.

The baseline policy matches exact stored Unicode spellings and reports paths as arrays of components. It compares object kind, POSIX mode and ownership, visible hard-link groups and counts, symlink targets, and regular-file data and resource forks. Forks compare by exact bytes and available stream presence. HFS+ exposes an empty stored resource descriptor as a zero-length stream. APFS reports absence when the resource attribute is missing. The report lists its policy, limits, and exclusions, including timestamps, Finder settings, allocation records, and signatures.

Use `--paths native` when both volumes expose the same qualified name profile. HFS+ and case-folded HFSX use the historical comparator on stored decomposed UTF-16. Binary HFSX uses exact stored UTF-16 units. APFS with both name-insensitivity flags clear uses exact stored UTF-8. Normalization-insensitive APFS uses canonical decomposition, with full case folding for a case-insensitive volume. These two APFS profiles admit scalars assigned through Unicode 9. Names outside that repertoire stop native comparison with a typed diagnostic, and `--paths exact` retains access to their stored spellings. Differing profiles and ambiguous paths fail with diagnostics. The library's `Limits::max_path_bytes` also bounds native key bytes independently on each side. [HFS+ catalog name comparison](https://developer.apple.com/library/archive/technotes/tn/tn1150.html#UnicodeSubtleties) [APFS name semantics](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html)

The native report includes the selected profile. A changed pair uses the stored left path and includes `right_path` when the spelling differs. `equivalent_path_spellings` records spelling differences for pairs whose compared fields agree. Path spelling differences under the native policy do not change the outcome on their own. Hard-link groups and rename inference use the paired namespace. The default `--paths exact` keeps stored spellings significant.

For the native path portion of D-REL-03, read-only HFS+ mounts on macOS 14.7.2 resolved case and composition variants to the same object. dmgez paired the nested paths and reported one changed data fork with both stored spellings. The same edits on a binary HFSX volume yielded three path additions and three removals under both modes. All image digests matched before and after the comparison. APFS bytewise mode follows the admitted on-disk catalog profile. This mount qualification covers HFS+ and HFSX. [Native path evidence](../../tests/compatibility/volume-read/native-paths-diff.json)

The APFS name oracle on macOS 14.7.2 verified canonical spelling variants on both case profiles and a full case-fold expansion on the folded profile. dmgez paired the nested paths and reported one changed fork with both stored spellings. Each volume contained two distinct files with the same recorded 22-bit name hash. The comparison reported only the edited member, which covers the A-READ-01-T02 collision case. Native comparison returned a code-point diagnostic for U+11F04, and exact comparison still admitted the image. All image digests matched after the checks. [Native APFS name evidence](../../tests/compatibility/volume-read/apfs/native-unicode-paths-diff.json)

With `diff-hash` compiled, use `--contents blake3` to hash equal-length data and resource forks on matched regular files. `--contents blake3-exact` also confirms matching digests with an exact stream comparison. Each pass consumes the shared byte budget. The hash pass reuses digests of validated hard-link storage within the same opened view and fork. Exact confirmation reads both forks for each matching path. Length and presence remain part of fork equality. Symlink targets, Finder settings, and optional extended attributes use their own comparison policies. The default is `--contents exact`.

Use `--infer-renames` to list candidate pairs among unmatched regular-file paths without shared hard-link storage. Each pair needs a unique data and resource fork fingerprint on each side, including fork presence and lengths, and at least one nonempty fork. The hash index lives for a single comparison. Candidates appear separately from the added and removed changes. Same-content deletion and copying can produce the same evidence as moving a file. The larger of the total fingerprint bytes read on either side charges the shared budget. Candidate fingerprints use BLAKE3 independently of the selected policy for matched files.

Add `--xattrs` to compare stored attribute names and exact values on common paths. Complete listings establish whether a name was added or removed, including a present empty value. Values for matching names share the fork payload budget. Reports contain names and change kinds. An uncheckable listing, invalid name, unreadable matching value, or exhausted budget stops the comparison. The policy identifies its name limits and excluded records for resource forks, Finder info, compression, symbolic links, and access-control lists. Quarantine records compare as stored bytes. Trust assessment remains separate.

Add `--finder-info` to compare the effective 32-byte FinderInfo and its presence on common paths of the same supported kind. HFS+ and HFSX read the catalog metadata behind each regular-file hard link, mask the kernel's private fields, and treat an empty projected value as absent. APFS reads one admitted FinderInfo representation from the owning inode or its inline attribute. Symbolic links are inspected in place. Reports identify changed paths with `finder_info` and omit the bytes. The comparison charges 32 bytes for a pair with a value on either side and stops if the selected reader cannot establish an object's FinderInfo. `--finder-info` uses the same composed reader as the baseline comparison and can be combined with either additional metadata policy. [HFS+ FinderInfo projection](https://github.com/apple-oss-distributions/hfs/blob/main/core/hfs_xattr.c#L288-L367) [Apple File System Reference](https://developer.apple.com/support/downloads/Apple-File-System-Reference.pdf#page=111)

With `finder-diff` compiled, add `--finder-layout` to decode the data forks of matching regular files named `.DS_Store`. The policy compares window, view, icon position, icon and list settings, and the admitted background alias facts. It matches records by exact stored name and FourCC and reports additions, removals, and changes by record identity. Unmatched stores appear as ordinary added or removed paths. Matching files still receive the other enabled comparisons, including resource forks, `--xattrs`, and `--finder-info`.

The Finder profile admits single-leaf stores within the reader's byte, record, name, and plist limits. The larger of the two complete store lengths is charged to the shared logical byte budget. Unsupported store profiles and decoding failures stop the comparison. The report lists excluded allocator layout, opaque record values, unreported settings and alias fields, and alias resolution. The default semantic policy compares `.DS_Store` data forks by exact bytes.

The comparison reads under bounded catalog and payload budgets. `--max-bytes` controls the compared logical payload bytes per side. Exit codes are 0 for equality under the reported policy, 1 for differences, and 2 for an unsupported operation, read error, or exhausted budget. Reports sort changes by stored path components. [Semantic CLI tests](../../apps/dmgez-cli/tests/semantic_diff_cli.rs)

### Lint project layout

The implemented `layout` profile evaluates one declared project folder at a time. The CLI and desktop editor use the same declared entries, implied directories, and preview geometry. It reports clipped or overlapping configured icon rectangles, icons outside the viewport, positioned hidden entries, automatic arrangement, and tight grid spacing. `--folder` selects a virtual folder and `--suppress RULE=REASON` retains the diagnostic with its suppression reason. `--json` includes the selected folder, viewport, stable rule IDs, and evidence. Linked source trees, mounted Finder behavior, labels, and release trust have separate qualification requirements.

The [layout service fixtures](../../crates/services/dmgez-lint/tests/layout.rs) and [CLI integration tests](../../apps/dmgez-cli/tests/lint_cli.rs) exercise the icon geometry and suppression portion of `D-REL-04-T01`. The full acceptance case also requires installer rules and native release checks.

### Lint installer inputs

Build with `installer-lint` and run `lint PROJECT --profile installer` to check the whole project. Discovery follows the builder's copy filters, bounds, and source identity checks. It inspects the planned image paths and can run before the output directory exists.

- A top-level `.app` calls for the `/Applications` shortcut. When present, the shortcut must be a symlink with exact target `/Applications`. Other symlinks with absolute targets or relative targets that lexically escape the image root produce findings. The analysis reads link text and checks its components without traversing chains of links.
- For each `.app` directory, the profile reads a bounded XML or binary `Contents/Info.plist` and checks the `CFBundleExecutable` entry. The value must be a single component naming a regular file under `Contents/MacOS`. It checks the captured POSIX execute bits and reports when they are unavailable or the project disables permission preservation. [Apple bundle executable key](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html)
- Explicitly referenced Finder backgrounds and Retina variants are checked for presence and regular-source identity. Image decoding and dimension checks run in build preflight.

`--json` reports stable rule IDs, warning severity, and evidence. `--suppress RULE=REASON` keeps the finding and reason in the report. Exit 0 means there are no unsuppressed warnings, exit 1 means warnings remain, and exit 2 means the inspection could not finish. The [installer CLI fixtures](../../apps/dmgez-cli/tests/installer_lint_cli.rs) check the link, background, executable-mode, and suppression portions of D-REL-04-T01. Signature, notarization, and native assessment require their own evidence.
