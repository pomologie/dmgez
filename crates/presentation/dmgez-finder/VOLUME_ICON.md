# Prebuilt volume icons

The optional volume-icon feature admits a prebuilt .icns file and borrows its original encoded bytes. A builder reserves .VolumeIcon.icns before catalog ID allocation, stores those bytes as the generated root asset, and applies the custom-icon flag to the root folder's catalog Finder information. The catalog field is distinct from the HFS+ volume-header field that contains boot and volume identity data. [Apple TN1150](https://developer.apple.com/library/archive/technotes/tn/tn1150.html#FinderInfo)

The parser limits the encoded ICNS file to 16 MiB, verifies every element boundary, and rejects duplicate element types. It accepts fixed-size modern PNG icon representations through 1024×1024 pixels and native small ARGB representations. It checks the PNG dimensions before decoding, rejects animation and trailing bytes, and verifies the CRC of every chunk. The icns crate validates image data one representation at a time with its PNG feature enabled. The largest decoded raster has 4 MiB of pixels. The PNG crate's default 64 MiB internal limit also applies. [icns 0.5.0](https://docs.rs/icns/0.5.0/icns/) · [png 0.18.1 decoder limits](https://docs.rs/png/0.18.1/png/struct.Limits.html)

An optional info record may carry a binary property-list dictionary. The validator streams up to 256 events from at most 4 KiB of encoded bytes. Repeated references therefore cannot expand into an unbounded owned property-list tree. The application preserves this data without interpreting the archived metadata. This module uses the unstable stream API of plist 1.10.4, as locked in Cargo.lock. Revalidate the stream's allocation, iteration, and error behavior when updating that package. [plist 1.10.4 BinaryReader](https://docs.rs/plist/1.10.4/plist/stream/struct.BinaryReader.html)

JPEG 2000, legacy icon elements, image generation, badging, and per-item icons require additional qualification. The validator performs no file I/O. Its caller reads a bounded, identity-checked local source and accounts for the decoder's working set.

## Native evidence

The checked-in tests/fixtures/apple-iconutil.icns began with ten synthetic two-color RGBA PNGs generated by tests/volume_icon_oracle.py. Apple iconutil on macOS 14.7.2 (23H311) combined them into eight PNG elements, two small planar ARGB elements, and one binary property-list info element. The same converter recreated the 53,650-byte file byte-for-byte and extracted all ten requested representations at their expected dimensions. The fixture uses generated geometry and colors. [Apple's iconutil instructions](https://developer.apple.com/library/archive/documentation/GraphicsAnimation/Conceptual/HighResolutionOSX/Optimizing/Optimizing.html)

On the same host a disposable HFS+ image returned 0 from GetFileInfo -aC before setting the flag and 1 after SetFile -a C. The mounted root's com.apple.FinderInfo reported the 0x0400 bit at bytes 8–9, and the asset read back exactly. After detaching and exporting raw sectors, the test independently found the bit in CNID 2's catalog folder record. It also checked the separate volume-header Finder information field.

A scratch integration with Rust 1.99.1 on aarch64-apple-darwin used the Finder validator and root flag API, the sibling HFS+ builder at 9db2cb9, and the UDIF writer at dmgez a4da64b with the local Finder changes. Apple verified the UDZO checksum and mounted the image read-only. GetFileInfo reported the custom-icon flag, the mounted ICNS matched the input, and the raw export placed the bit in the root catalog record.

The TOML runner then resolved a relative source with its `--volume-icon` feature enabled. The local integration used dmgez 049ab26 with the builder changes and hfsplus 5c87256. Dry-run reported both Finder assets without creating the output. Apple verified the 31,236-byte UDZO file, mounted its 94,208-byte logical HFS+ volume read-only, reported the custom-icon flag, and returned every input ICNS byte. The separate raw catalog check passed.

These observations cover prebuilt asset admission, TOML build, and root flag placement for D-FINDER-01-T01 and D-FINDER-03-T01, plus the representation and wrong-dimension checks of D-FINDER-03-T02. Native Finder rendering still requires a separate check.
